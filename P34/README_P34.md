# P34 — WFA BounceTrader, standalone EXE (аналог P33 для bounce-стратегии)

Дата сборки: 2026-11-09. Ты ничего не компилируешь: в пакете готовый
`wfa_bounce.exe` + данные + скрипт проверки. Всё работает офлайн.

## Зачем этот пак

Твой локальный cargo падает на больших release-сборках (rustc 0xc0000005 на
фазе fat-LTO — известная проблема компилятора, не ошибка кода). P33 уже решил
это для momentum: готовый EXE собрал всё без единой компиляции, и у тебя он
прошёл **12/12 MATCH** — числа совпали с эталоном P31 байт-в-байт.

P34 делает то же самое для второй стратегии — **BounceTrader** (RSI-отскоки от
фрактальных уровней, тот самый кандидат «bounce» из гейта P29/P30b):

1. теперь и bounce можно проверить локально 1:1 без cargo;
2. твой собственный `src\bin\wfa_bounce.rs` проходит контроль происхождения:
   EXE собран ровно из того файла, что лежит у тебя в src.rar
   (SHA256 `4d893fbcfd71304b33ad0e6bbc89fe0569e994e27e3b6f85216da5a6d5b3b976`),
   никаких расхождений между «моим эталоном» и «твоим деревом» нет.

## Как собран (провенанс)

| Параметр | Значение |
|---|---|
| Исходник | `src/bin/wfa_bounce.rs` из твоего src.rar, P30 v2, SHA256 выше |
| Компилятор | rustc 1.99.1 (тот же, на котором снимался эталон P30b) |
| Цель | x86_64-pc-windows-gnu (Windows x64, PE32+), кросс-сборка llvm-mingw |
| Профиль | lto=false, codegen-units=16 — чисел НЕ касается: f64-арифметика
детерминирована IEEE754 и от LTO/профиля не зависит (P33 это доказал на
практике: у тебя на машине 12/12 MATCH с эталоном песочницы) |

## Приёмка

Скрипт сам выполнит 5 прогонов (те же команды и флаги, что в README_P30b,
только вместо `cargo run` — exe) и сверит n / WR / R / PF с эталоном P30b:

| Прогон | Данные | Ожидание (эталон P30b) |
|---|---|---|
| run_fresh_2026 | BTC 450d | n=18 WR=55.6% R=+7.15 PF=1.72 |
| run_fresh_stress | BTC 450d, fee .0006 spr .0003 | n=11 WR=45.5% R=+0.97 PF=1.13 |
| eth | ETH 450d | n=13 WR=38.5% R=-0.61 PF=0.94 |
| sol | SOL 450d | n=5 WR=0.0% R=-6.35 PF=0.00 |
| btc720 | BTC 720d, 20 фолдов | n=26 WR=50.0% R=+5.81 PF=1.36 |

В конце должно быть напечатано:

```
RESULT: OK - all 5 reference runs match the P30b etalon 1:1.
```

Каждый прогон занимает меньше секунды. Если где-то MISMATCH или PARSE_FAIL —
пришли все `run_*.log` из папки P34, этого хватит для диагноза.

## Что означают числа (честно, без ретуши)

- **BTC 450d**: R=+7.15, PF=1.72 — плюс есть, но сделок 18 (< 20), и нижняя
  граница 95% CI отрицательная (-4.90). Статистически это «обещающе», а не
  «доказано».
- **Стресс (двойные издержки)**: +0.97R — выживает, но впритык.
- **ETH**: -0.61R, **SOL**: -6.35R (CI [-6.62;-6.03] — даже ВЕРХНЯЯ граница
  ниже нуля). Плюс BTC на другие инструменты НЕ переносится.
- **BTC 720d (20 фолдов)**: n=26, R=+5.81, но CI_lo=-8.93 и WR=50% — выборки
  при 0.05 сделок/день физически не хватает, чтобы CI сомкнулся в плюсе.

Отсюда вердикт гейта P29/P30b: **2/5, гейт НЕ пройден** — bounce остаётся в
бумажном парке (полное обоснование — README_P30b, раздел «Гейт P29 на свежих
числах»). P34 не меняет этот вердикт — он даёт тебе возможность ПОДТВЕРДИТЬ
его на своей машине без компилятора.

## Что exe НЕ делает

Чистый offline-расчёт по CSV: читает `--data`, пишет `--out` каталог
(summary.json / per_fold.csv / oos_trades_production.csv) и stdout. Сеть,
биржи, API-ключи, аккаунты — не трогает вообще (только std, никаких сетевых
крейтов).
